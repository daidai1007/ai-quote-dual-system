# 柜体材料明细数据库与程序上线人工步骤

本目录只提供人工执行材料。本地工作未连接或修改线上数据库，也未部署 Render API 或客户端。

## 数据依据

- 文件：`JS,JP,JA,JE,JK,JM材料明细-面积公式.xlsx`
- SHA-256：`91cc0a5f841b74559a34a7408a604e41d5fe76e8db3743b20a32ff657c2b2151`
- 数据版本：`cabinet-material-91cc0a5f841b7455-v1`
- 柜体规则：241 条；默认废料系数 1.2，程序传值优先。

## 执行顺序

1. 在 Neon production / neondb 新建 SQL Editor，完整运行 `web/00-preflight.sql`。确认 SECC、SUS304、SUS316 均有密度，存在 `calc.get_material_unit_price(varchar,date)` 和 `calc.calculate_dual_quote`。如结构不同，停止，不改脚本绕过。
2. 完整运行 `web/01-create.sql`（内容与 `database/migrations/cabinet_material_v1.sql` 一致）。这是加表、加快照列和创建导入/切换函数；不切换活动版本，不修改附件数据和报价历史。
3. 完整运行 `web/02-stage.sql`。成功结果必须是 `cabinet-material-91cc0a5f841b7455-v1`。
4. 完整运行 `web/03-validate.sql`。必须得到 241 条、6 个产品族、默认系数 1.2，并核对门型/料厚分组。
5. 部署包含 `api/cabinet_material_service.mjs` 和本次 `api/server.mjs` 修改的 Render API。此时目录仍为 STAGED，API 会继续使用旧路径，便于先做健康检查。
6. 发布新版客户端。旧客户端未发送 `waste_factor` 时仍可兼容，服务端使用默认 1.2；新版客户端可输入废料系数和箱体料厚。
7. 在维护窗口运行 `web/04-activate.sql`。事务只更新版本状态，使用事务级 advisory lock；并发请求可能有很短的行锁等待，`lock_timeout=5s` 会在锁竞争过久时整体回滚。
8. 分别以 SECC、SUS304 做代表性报价，并将废料系数从 1.2 改为 1.3。核对净重不变、计价重和材料成本按比例变化；固定 SECC 明细的密度/单价不随程序材质改变；动态附件金额不变。
9. 运行 `web/05-verify.sql`。`invalid_fixed_material_rows` 必须为 0，活动版本只能有一个，快照列应返回 5 行。
10. 确认 API 报价、保存重开和导出均通过后，运行 `web/06-delete-retired.sql`，删除替换表中的旧版本规则。该步骤不删除历史报价快照。

## 旧表处理与兼容边界

`calc.cabinet_part_rule` 不是单纯的旧重量表，它还提供喷塑面积和已发布客户端的公式模板。当前不能 `DROP` 或整表 `DELETE`；这样会同时破坏喷塑计算。新 API 已绕过其中的重量结果，并以新表计算最终材料成本。待所有客户端升级且喷塑规则另行迁移后，才能单独安排删除该共享旧表。本次可执行的旧数据删除是第 10 步：删除新柜体材料目录中已经 RETIRED 的旧版本。

不要运行 `TRUNCATE CASCADE`，不要清空 `dual_quote_result`、附件选择或其他历史表。并柜汇总规则本次不修改；每个子柜仍独立调用 API，并携带同一笔报价所输入的废料系数。
